# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Tuners Toolkit is a Kotlin Multiplatform / Compose Multiplatform app for ECU calibration editing. It loads an ECU firmware image (Intel HEX) plus its ASAM MCD-2 MC description (`.A2L`), decodes the calibration maps (values, curves, maps) from the binary, and lets the user browse and edit them in a hex/ASCII editor and in map grids. Targets: **desktop (JVM), Android and web (wasmJs)**, plus iOS when built on a Mac.

**`docs/PLAN.md` is the roadmap** (phases, target architecture, file formats, UI kit). Check it before larger changes, and tick its boxes as phases land. Package root everywhere is `org.mr0btain.tunerstoolkit`. Dependency versions follow TicketMan's (`github.com/Mr0btain/TicketMan`), since the two will share a UI kit.

## Commands

```bash
./gradlew :composeApp:run                    # desktop app (main: org.mr0btain.tunerstoolkit.MainKt)
./gradlew :composeApp:wasmJsBrowserDevelopmentRun   # web app in a browser
./gradlew :androidApp:assembleDebug          # Android APK
./gradlew :composeApp:packageDistributionForCurrentOS   # desktop installer (Dmg/Msi/Deb)

./gradlew :core:jvmTest                      # core tests
./gradlew :core:jvmTest --tests "*.TkResultTest"     # one test class
./gradlew :composeApp:desktopTest            # app tests (commonTest + desktopTest)

# Quick compile checks
./gradlew :composeApp:compileKotlinDesktop :composeApp:compileKotlinWasmJs :composeApp:compileAndroidMain
```

The version every package is built as is `tunerstoolkit.version` in `gradle.properties`. All modules use a JDK 21 toolchain (`jvmToolchain(21)`); Gradle downloads it through the foojay resolver if it isn't installed. CI (`.gitea/workflows/ci.yml`, copied to `.github/workflows/ci.yml` for GitHub) runs both test tasks and the web, desktop and Android builds on every pull request and push to `main`. GitHub also compiles iOS on a Mac, with `continue-on-error` until it has passed once. There's no lint task. `docs/testing.md` covers where tests go and how to use real ECU files.

**Shared libraries**: Tm-AppLogger and Tm-UI-Kit (TicketMan uses them too) are built from source through `includeBuild` in `settings.gradle.kts`, from the first of `<sharedLibsDir>/<name>` (a Gradle property), `../<name>`, or `.deps/<name>`, which is cloned from `github.com/Mr0btain/<name>` at the tag pinned there. A change in a local checkout shows up here immediately. Bumping a library means changing its tag in `settings.gradle.kts` and its version in `gradle/libs.versions.toml`. The UI kit is a dependency of `composeApp` (package `org.mr0btain.uikit`, `Tm*` components, `TmTheme`), and every screen is built from it.

**Real ECU files never go in git** (usually OEM copyrighted). They live in git-ignored `testdata/local/`. For tests and demos use **TT-DEMO-1** in `testdata/demo` (a made up HEX and A2L generated by core's `DemoEcu`; `DemoFilesTest` keeps them in sync, and `-DregenerateDemo=true` rewrites them). On desktop, `readTestDataFile()` reads from `testdata/`, and the files screen's **Open the demo** opens both demo files.

## Modules

- **`core`**: KMP library (android, jvm, wasmJs, iOS on Mac) with **no Compose**. It's for logic testable with plain `kotlin.test`. So far it holds:
  - Logging comes from **Tm-AppLogger** (`org.mr0btain.applogger`, an `api` dependency, so `composeApp` sees it too). `AppLogger.e/w/i/m/d(tag, message, throwable?)` writes to the platform log and keeps each line in `LogBook`. `d` only writes when `AppLogger.debug` is on. Use hierarchical constant tags: `private const val TAG = "Thing"`, then `"$TAG:Function"`. Never log file contents. On desktop, `main.kt` attaches a `LogFileStore` (daily `tunerstoolkit-<date>.log` files under the app data dir's `logs/`).
  - `error/TkResult`: a `TkResult<D, E : Error>` (`Error` is a `LogMessage`, so it can be logged as is) (`Success`/`Failure`) with `map`, `flatMap`, `onSuccess`, `onFailure`, `getOrNull`, `valueOr`. New code returns this instead of throwing.
  - `image/MemoryImage`: an ECU image as sorted, separate segments of bytes (addresses are `Long`, up to 0xFFFFFFFF). Lookups are a binary search over segments. It has typed reads and writes (`readUnsigned/readSigned/readFloat32/readFloat64`, the `write*` matches, all with a `ByteOrder`), and `readInto` for drawing rows that run into gaps. Every write is a `Patch`; `edit { }` groups writes into one undo step, and `undo()/redo()` walk them. `changedRanges()`/`patchesFromOriginal()` compare with the image as loaded, and `diff(other)` compares two images. Its layout is fixed once built: `MemoryImage.Builder` joins touching pieces, keeps the last bytes where pieces overlap, and lists the overlaps.
  - `formats/binary/`: `IntelHex` (record types 00-05) and `SRecord` (S0-S9) readers and writers, `RawBinary` (the base address comes from outside the file, gaps are filled with 0xFF when writing), `BinaryFormat.detect` (by content, not file name), and `BinaryImport.read` to read whichever format a file is in. Readers never throw: a broken record is left out and reported as a `Diagnostic` with its line and column, and only an empty or dataless file fails (`ImportError`). Results are `TkResult<Imported<T>, ImportError>`, where `Imported` carries the value and its diagnostics.
  - `diagnostics/Diagnostic` and `Diagnostics`: parse, decode and export problems with severity, `SourceLocation` and object name. Parsers report these instead of dropping things silently.
  - `project/`: projects with versions. `ProjectRepository` keeps each one in a `ProjectStore` as `projects/<id>/project.json` (`ProjectManifest`), `source.bin` (the file as it was read), `versions/<id>.json` (that version's patches from the original) and optionally `definition.bin` (its A2L). `FileSystemProjectStore` (kotlinx-io) is the store on desktop, Android and iOS, and `MemoryProjectStore` is for tests. `ProjectManifest.ORIGINAL` is the read-only original.
  - `image/ByteText`: bytes as hex or ASCII text and back, for copy and paste.
  - `a2l/`: the new A2L reader. `A2lText` picks the encoding, `A2lLexer` streams tokens (with line and column), and `A2lParser` builds an `A2lTree` of `A2lElement`s using `A2lSpec`, the table of every keyword's parameters (add a keyword there, not in the parser). A2ML and IF_DATA are kept as raw text; `A2ml` parses the grammar. `A2lModelBuilder` makes the typed model (`A2lFile` → `A2lModule` → `Characteristic`, `AxisPts`, `CompuMethod`, `RecordLayout`, …), where references are still names. `A2lImport.read` does all of it and returns `TkResult<Imported<A2lFile>, ImportError>`.
  - `calibration/`: the one definition model every format maps into. `CalibrationObject` (kind, address, `Storage` = its record's `RecordField`s in order, `CalibrationAxis`es with an `AxisSource`, and a `Conversion`) is resolved: no names left to look up except shared axes, which `CalibrationSet` finds by name. `CalibrationCodec.decode` reads one from a `MemoryImage` into `CalibrationValues` (values always in x first order, axes, the memory `ranges` it occupies), and `write`/`writeRaw`/`writeText`/`writeAxis`/`writeAscii` put edits back, checked against limits and the type's range. `DataType` (UBYTE … FLOAT64_IEEE, with `readNumber`/`writeNumber`) and `Expression` (FORM formulas, evaluated by walking a parsed tree) live here too. `a2l/A2lResolver` turns an `A2lModule` into a `CalibrationSet`. `ObjectIndex` (built by decoding every object against an image) says which objects' parts (`ObjectPart`: values, axis points, record) are at an address; `formatValue` applies an A2L FORMAT. In `a2l/`, `EpkCheck` compares MOD_PAR's EPK with the image, and `A2lWriter` writes a tree (or a subset of objects) back to A2L text.
  - A generated `BuildInfo.VERSION`.

  `formats/` beyond binaries: `xml` (a lenient XML reader and writer, depth capped), `xdf` (TunerPro XDF definitions in and out), `ttdef` (our own definition JSON), and `values` (calibration values by name: `CalibrationData` turns objects into `DataRecord`s and applies records back as one undo step; `Dcm`, `Cdfx`, which also reads PaCo, and `Csv`). `calibration/ManualMap` makes the objects for a map defined by hand.

  `checksum/`: generic checksum algorithms, checks and fixing (`Checksums`), and ECU family modules (`.ttsum` JSON via `TtSum`, or Kotlin `ChecksumModule`s), registered in `ChecksumModules`. `docs/checksums.md` says how to add a family.

  `finder/MapFinder`: suggests maps in an image without a definition (counted records and bare rising axes, scored by how smooth the values are); a `FoundMap` becomes a `ManualMap`.

  `calibration/` also has the map editing logic: `ObjectTree` (the map list's rows, with search; `a2l/A2lFolders` makes the FUNCTION and GROUP folders), `MapEdit` (set, add, multiply, add %, interpolate by axis values, smooth, and spreadsheet paste over a `CellSelection`), `writeAll` (many values as one undo step, clamped to the limits), `Tsv`, and `Compare` (two images' differences mapped to objects, and copying an object's bytes across).
- **`composeApp`**: KMP Compose UI: screens, handlers and this app's kit components. It's built as an Android **library** (`com.android.kotlin.multiplatform.library`) plus `jvm("desktop")` and `wasmJs` (iOS only on macOS).
- **`androidApp`**: a thin Android application around `composeApp` (`MainActivity`). It sets `appContext`, which the project store and settings read, before `setContent`. It also does release signing from the `TUNERSTOOLKIT_KEYSTORE*` env vars or Gradle properties.
- **`iosApp`**: Xcode project. It's not compiled on Linux.

## Architecture

`App.kt` is the app: `TmTheme` and the kit's `TmAppShell` (a nav rail on desktop and wide windows, a bottom bar on phones) around a `Destination` (Files, Editor, Find maps, Versions, Compare, Checksums, Log, Settings, and Gallery, which Settings opens).

### State: small handlers, made in `App`
No view model and no DI; each handler is a `@Stable` class with Compose state, made once in `App` and passed to the screens that need it. Tests make them with `inBackground`/`readInBackground = false` so work happens straight away.
- `ui/document/DocumentHandler`: the open `MemoryImage` read through core's `BinaryImport`, every write (`write`, and `edit { }` for codec writes as one undo step), undo and redo, find and export; `version` is state so views redraw. `onDocumentChanged` tells other handlers when another image opens, and `original()` is the image as it was opened.
- `ui/project/ProjectHandler`: saved projects, which project and version is open (`current`), saving, renaming versions, `branch` (a new version from an old one) and `versionImage` (a version as its own image). Every open goes through it, so `current` matches the editor. The open definition is saved with a project (`definition.bin`) with any maps made by hand (`additions.ttdef`), and both open with it.
- `ui/definition/DefinitionHandler`: the open definition (`OpenDefinition`: an A2L, XDF or .ttdef read by content, plus maps made by hand as `additions`, with the map list's `groupings`) resolved into one `CalibrationSet`, and `onImage`: the object index, EPK check and overlaps for the open image, rebuilt in the background whenever another image opens. `decode(obj)` reads an object from the open image.
- `ui/editor/EditorHandler`: the editor's map tabs (`OpenMap`: its `MapTableState` and view), which is in front, the selected object, and the map list's mode, search and open folders. Kept while other screens are open.
- `ui/exchange/ExchangeHandler`: values in (DCM, CDFX, PaCo) and out (DCM, CDFX), a map as CSV both ways, the map list as CSV, and the definition saved as .ttdef or XDF. The last import's report stays for the files screen.
- `ui/checksum/ChecksumHandler`: the open image's checksum module (detected or picked), your own checks, the results (worked out again in the background after edits), and fixing. Its module and own checks are `ProjectAttachment`s: `ProjectHandler` saves anything that implements that with the project as a named file.
- `ui/finder/FinderHandler`: the map finder's options, a run in the background (progress, Stop), its suggestions and adding one as a map made by hand.
- `ui/compare/CompareHandler`: what the open image is compared with (its original, a version or a file), the `ImageComparison` (redone after edits), and copying a map across.
- `ui/settings/SettingsHandler`: `SettingsData`, saved on each change through `SettingsStorage` (expect/actual: the old `settings.sts` locations, localStorage on the web).

`platformProjectStore()` is expect/actual: `<user data dir>/TunersToolkit/store` on desktop, `files/store` on Android, Application Support on iOS, and the Origin Private File System on the web (`OpfsProjectStore`, falling back to memory).

### Screens
- `ui/files`: open an image and a definition (or both demo files), the projects list, the calibration values panel (import with its report, export), the definition report (with saving as .ttdef, XDF or a map list CSV) (`DefinitionPanels`: objects, how many were read from the image, what was left out and why, overlaps, the EPK check) and the image's import report. `rememberFileSaver` is expect/actual (FileKit's save dialog, or a download on the web); `readTestDataFile()` reads the checkout's `testdata/` on desktop only.
- `ui/editor`: the map list (`MapList`: by the definition's groupings or all, with search, and New map for `ManualMapDialog`) beside tabs for the hex view and each open map (`MapPane`: table, chart or 3D surface, cube slice pickers, the selection operations, details). Below 900dp the list is a tab. In the hex view the definition's objects are tinted, double-click opens one, and the status line names the object, cell and value under the cursor. Map edits go through `CalibrationCodec.writeAll` (clamped to the limits, one undo step).
- `ui/versions`: the open project's versions as a timeline (open, compare, rename, start a new version from one, delete) and its info.
- `ui/finder`: the Find maps screen (options, suggestions by confidence, a preview, Add as a map).
- `ui/checksum`: the Checksums screen (module, every check, Fix all, adding your own).
- `ui/compare`: the open image against its original, a version or a file: what changed by map, each map as this / other / difference, copy a map across, and changes outside maps.
- `ui/log` (`LogBook` through `TmLogTerminal`), `ui/settings`, and `ui/gallery` (the kit's gallery plus this app's sections).

### This app's kit components (`ui/kit`)
Tm prefix, built from Tm-UI-Kit pieces, each with a gallery entry. They take colors and type from `TmTheme` and aren't checked by `UiKitRulesTest`.
- `ui/kit/hex`: the hex view. `HexRows` maps rows to addresses by binary search over blocks of segments, with one row per gap. `HexViewState` holds the cursor, selection and display as byte addresses. `TmHexView` puts one Canvas on each lazy row, with its text measured once and kept until the bytes change; it never writes itself (edits go to `onWrite`). `HexClipboard` holds copy and paste; `Clipboard.writeText`/`readText` are expect/actual. `HexScrollbar` jumps straight to rows and marks changes, objects, the search match and the cursor. `HexMarks` tints bytes that belong to something, by role, in a tone fixed per name.
- `ui/kit/map`: `TmMapTable` (a lazy grid of Canvas rows: axis headers, low to high tints, changed cells marked against an original, selection by click, shift and drag, typing a number and Enter to set, +/- to step one stored unit, spreadsheet copy and paste, and This/Other/Difference modes for comparing; it never writes, changes go to `onChange`), `TmMapChart2D` (rows as lines, the original dashed) and `TmMapChart3D` (a surface drawn back to front on a Canvas, turned by dragging).

`UiKitRulesTest` runs Tm-UI-Kit's `KitRules` over `ui/` (not `ui/kit`) and `App.kt`. `ScreenRenderTest` draws the screens with the demo image and A2L to `composeApp/build/screen-renders/*.png` (the map editor too), so you can look a change over without running the app.

### Platform-specific code (`expect`/`actual`)
- `Platform.kt` → `getPlatform()`. The name is "Java", "Android", "Web" or iOS.
- Desktop finds the OS's app data folder through JNA `platform/*DirectoryResolver`s. Android code gets its `Context` from `appContext`, which `MainActivity` sets before `setContent`.
- File picking is common: FileKit's `rememberFilePickerLauncher` (all files, since A2L/HEX have no MIME type on Android).
- Anything in `commonMain` must also compile for wasm, so use `Dispatchers.Default`, not `Dispatchers.IO`, and no `java.*`.

### Resources
Compose resources live in `composeApp/src/commonMain/composeResources/drawable/` (the `tt_` icons: 64 px black line drawings, tinted where they're drawn), accessed through the generated `tunerstoolkit.composeapp.generated.resources.Res`. Fonts come from the UI kit. Web page shell: `composeApp/src/wasmJsMain/resources/index.html`. Android launcher icons, strings and the manifest are in `androidApp/src/main/`.
