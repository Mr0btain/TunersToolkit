# Architecture

Tuners Toolkit is Kotlin Multiplatform with Compose Multiplatform for the UI. One codebase builds the desktop app
(JVM), the Android app and the web app (Kotlin/Wasm), and the iOS app on a Mac.

## Modules

```
TunersToolkit/
├── core/          The logic, with no Compose: formats, the calibration model, editing, checksums, projects.
│                  Targets jvm, android, wasmJs (and iOS on a Mac). Tested with plain kotlin.test
├── composeApp/    The UI: App.kt, the screens, their handlers and this app's own kit components.
│                  An Android library plus jvm("desktop") and wasmJs
├── androidApp/    A thin Android application around composeApp (MainActivity), with release signing
├── iosApp/        The Xcode project
├── testdata/demo/ TT-DEMO-1, a made up image and A2L generated by core's DemoEcu
└── tools/         make_icons.py, which draws the app icon for every platform
```

Two shared libraries come from source through `includeBuild` in `settings.gradle.kts`:
[Tm-UI-Kit](https://github.com/Mr0btain/Tm-UI-Kit) (`org.mr0btain.uikit`, the `Tm*` components and `TmTheme`) and
[Tm-AppLogger](https://github.com/Mr0btain/Tm-AppLogger) (`AppLogger` and `LogBook`). Gradle uses a checkout next to
this project if there is one, and otherwise clones the pinned tag into `.deps/`. TicketMan uses both libraries too.

## From a file to a map on screen

```
bytes ──BinaryImport──▶ MemoryImage ◀──────────────── every edit is a Patch (undo, redo, diff)
                            │
.a2l / .xdf / .ttdef ──▶ CalibrationSet ──CalibrationCodec.decode──▶ CalibrationValues ──▶ TmMapTable, charts
  (A2lImport + A2lResolver,     │                                          │
   Xdf, TtDef)                  └──ObjectIndex: which object is at an address ──▶ hex view tints, tooltips
```

1. **The image.** `BinaryImport.read` recognises Intel HEX, S-record or raw binary from the content and builds a
   `MemoryImage`: sorted segments with gaps, looked up by binary search. Every write is a `Patch`, and `edit { }`
   groups writes into one undo step. `patchesFromOriginal()` is what a saved version stores.
2. **The definition.** A2L, XDF or `.ttdef` is read into one model, a `CalibrationSet` of `CalibrationObject`s, with
   nothing left to look up by name except shared axes. Each object has its kind, address, storage layout, axes and
   conversion. See [formats.md](formats.md).
3. **Decoding.** `CalibrationCodec.decode(obj, image)` gives `CalibrationValues`: physical values in x-first order,
   the axes, and the memory ranges the object covers. `writeAll` puts edited values back, kept within the limits,
   as one undo step.
4. **Indexing.** `ObjectIndex` decodes every object against the image, so the hex view can say which map, axis or
   record a byte belongs to.

Everything that can fail returns `TkResult<D, E : Error>` rather than throwing. Problems in files are reported as
`Diagnostic`s, with the line, column and object name, so nothing is dropped silently.

## The app

`App.kt` is `TmTheme` and the kit's `TmAppShell`: a nav rail on desktop and wide windows, and a bottom bar on phones.
The destinations are Files, Editor, Find maps, Versions, Compare, Checksums, Log, Settings and Gallery.

There's no view model and no dependency injection. Each piece of state is a small `@Stable` **handler** with Compose
state, made once in `App` and passed to the screens that need it:

| Handler | Holds |
|---|---|
| `DocumentHandler` | The open image, every write, undo and redo, find and export |
| `ProjectHandler` | Saved projects and versions, and which one is open |
| `DefinitionHandler` | The open definition, and its object index and EPK check against the open image |
| `EditorHandler` | The map tabs, the selected object, and the map list's mode and search |
| `ExchangeHandler` | Values in and out (DCM, CDFX, PaCo, CSV), and saving the definition |
| `ChecksumHandler` | The checksum module in use, your own checks and modules, and fixing |
| `IdentHandler` | What the image says it is (part numbers, software numbers, VINs) |
| `FinderHandler` | The map finder's runs and suggestions |
| `CompareHandler` | What the image is compared with, and copying maps across |
| `SettingsHandler` | Settings, saved on each change |

Handlers do heavy work on `Dispatchers.Default` and can be told to work straight away instead, which is how the
tests use them.

### Storage

`platformProjectStore()` gives a `ProjectStore`, a small tree of files under one root:

- desktop: `<user data dir>/TunersToolkit/store`
- Android: `files/store`
- iOS: Application Support
- web: the browser's Origin Private File System, or memory where there isn't one

Inside it are `projects/<id>/` (the manifest, the file as it was read, each version's patches, and the definition)
and `checksums/` (your own checksum modules).

### Platform code

`expect`/`actual` is kept to a few places: the platform name, the project store, settings storage, the clipboard,
the file saver and the desktop's data folders. File picking is FileKit everywhere. Code in `commonMain` also has to
compile for Wasm, so it can't use `java.*` or `Dispatchers.IO`.

## UI kit components

Every screen is built from Tm-UI-Kit. Components only this app needs live in `composeApp/.../ui/kit/` with the same
`Tm` prefix, each with a Gallery entry:

- `hex/`: `TmHexView`, a Canvas per lazy row with tints and outlines per map
- `map/`: `TmMapTable`, `TmMapChart2D` and `TmMapChart3D`
- `tabs/`: `TmClosableTabs`
- `tooltip/`: `TmTooltip`, `TmTipButton` and `TmPointerTooltip`

`UiKitRulesTest` checks that screens outside `ui/kit` use the kit rather than raw Material, and `ScreenRenderTest`
draws every screen, wide and at phone width, to `composeApp/build/screen-renders/`.
